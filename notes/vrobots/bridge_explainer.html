Why ROS 2 cannot talk to the Pixhawk directly

ROS 2 nodes speak DDS. Full DDS is too large for a microcontroller, so PX4 speaks XRCE-DDS, a lightweight version made for small chips. XRCE-DDS is a client protocol: by design, a client can only talk to an Agent, never to a ROS 2 node.

Is the Agent inside the Pixhawk?

No

It is a normal program on the PC or companion computer. You start it yourself: MicroXRCEAgent serial --dev /dev/ttyUSB0 -b 921600 or MicroXRCEAgent udp4 -p 8888.

Is the Agent a ROS 2 node?

Not quite

It is a standalone program and does not need ROS 2 installed. It creates DDS publishers and subscribers on PX4's behalf, so to ROS 2 it looks exactly like a node. ros2 topic list shows the /fmu/... topics.

Does the bridge talk to the Agent?

No

The bridge only publishes and subscribes to ROS 2 topics. The Agent picks those up from the DDS network and forwards them to PX4 on its own.

PX4 believes it is flying. The bridge gives it simulated sensor readings. PX4 computes four motor outputs. The bridge turns them into pulse widths and the simulated quadrotor moves.

No Agent, no ROS 2, no firmware change. One USB cable and one program. This is the only path that can fly the simulated drone, because only MAVLink HIL accepts raw sensor data.

Here the bridge is an ordinary ROS 2 node. It publishes /fmu/in/vehicle_visual_odometry from simulator truth, and republishes the simulator as standard topics such as sensor_msgs/Imu and sensor_msgs/Image. Your offboard node publishes /fmu/in/trajectory_setpoint.

This path carries high-level data only. PX4's topic list accepts setpoints and odometry, but not raw IMU data, and it does not send motor outputs. Case B alone cannot fly the simulated drone.

Which sensors does EKF2 actually use?

One parameter decides it: SYS_HITL. It is read once at boot by the startup script. The choice of MAVLink or ROS 2 does not decide it.

SYS_HITL=0 (normal)

Boot
The board's real sensor drivers start. pwm_out and dshot drive the real motor pins.
EKF2 uses
The real IMU, magnetometer and barometer on the Pixhawk.
HIL_SENSOR
Ignored.
Over DDS
You can add vision odometry and send setpoints. You cannot replace the IMU.

SYS_HITL=1 (HITL)

Boot
Real sensor drivers are not started. GPS is disabled. pwm_out_sim replaces the real motor outputs, so the pins stay silent.
EKF2 uses
Only what arrives in HIL_SENSOR and HIL_GPS: the simulator's IMU, magnetometer, barometer and GNSS.
Then
Position, velocity, attitude and rate control run unchanged, then the control allocator.
Output
Motor values return to the PC as HIL_ACTUATOR_CONTROLS, at up to 200 Hz.

"No code change" means this switch already exists in stock PX4. The work is setting SYS_HITL=1, selecting a quadrotor airframe, rebooting, and sending the right MAVLink messages from the bridge.

ROS 2 over XRCE-DDS has no equivalent switch. Its topic list has no raw IMU input and no motor output, so it cannot run this loop by itself. With SYS_HITL=1 set, it still works beside MAVLink for setpoints and vision.
